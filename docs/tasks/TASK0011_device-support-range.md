# 対応する端末の範囲を決める

## 目的

アプリが対応する端末と OS の範囲を、根拠を添えて決める。テストと実機の検証で当てる値の
組を、その範囲から導けるようにする。

## 目標

- 端末と OS の違いのうち、画面の見え方と動作に効く軸をひととおり列挙する
- 軸ごとに、対応する範囲と、その根拠を決める
- 決めた範囲から、自動テストで当てる画面サイズと文字サイズの組、および実機の検証に使う
  エミュレータの構成を導く
- 起動から今日のページを操作できるまでの時間の目標値を、測る端末の条件と合わせて決める

## 非目標

- 決めた範囲に合わせて、既存の画面を直さない。直す必要が見つかれば、その画面の作業書へ
  書く
- iOS のビルドと検証をしない（Mac が要る）

## 問題

- 対応する OS の版の下限を定めていない（`requirements.md`「プロジェクト憲章」の問題）。
  いまの値は Android が Flutter の既定の `minSdk` 24、iOS が Deployment Target 15.0 である
- TASK0002 は、画面を 360 x 640 dp、文字の最大を Android 2.0 倍・iOS の AX5 と仮定して
  確かめた。この仮定より狭い端末がある（iPhone SE 第 1 世代の幅は 320pt）
- 列挙する軸の候補（着手時に洗い直す）:
    - OS の版（各 OS のサポート期限を一次情報で引く）
    - 画面の幅と高さ（小型の機種・タブレット・折りたたみ端末）
    - 文字サイズの最大値（Android の 200%・iOS のアクセシビリティの文字サイズ）
    - 表示サイズ・画面表示の拡大
    - 画面の向き（横向きを対象に含めるか）
    - ナビゲーションの形（3 ボタン・ジェスチャー）と画面の切り欠き
- TASK0002 の自動テストの画面（`useSmallPhone`）は、OS が使う余白（状態の帯・
  ナビゲーションの帯・切り欠き）を 0 にしている。導く画面の組には余白を含める
- 起動時間には目標値が無い。TASK0002 は release ビルドで測って残しただけで、後続の作業が
  起動の読み込みを増やしても、退行を判定できない
- TASK0002 の今日のページは、360 x 640 dp・iOS の AX5・状態の帯 24 dp で、記録の欄が
  起動直後 2 dp、アプリのヘッダーが流れた後 58 dp になる（テストのフォントで測った）。
  はみ出しと重なりは無いが、段のボタン（高さ 75 dp）が欄に収まらない。対応範囲を決める
  ときの判定に使う
    - 状態の帯の 24 dp は Android の値で置いた。iPhone の safe area は機種ごとに別に引く
    - TASK0013 で下端のナビゲーション（68 dp）が加わり、ナビゲーションの名前と注意書きの
      帯の文字を OS の設定によらず固定した（帯は 48 dp）。同じ条件で起動直後の記録の欄は、
      iOS の AX5 で 88 dp、Android 2.0 倍で 268 dp になり、Android 2.0 倍では全体の体調の
      段が起動直後に欄の内側に入る。横向き（640 x 360 dp・状態の帯 24 dp）では Android
      2.0 倍の欄が 100 dp で、iOS の AX5 は 105 px はみ出す。iOS の AX5 の横向きは
      TASK0013 の前からはみ出す（TASK0013 の作業記録）
- TASK0002 の設定のページは、iOS の AX5 で欄の名前（日付が変わる時刻）が末尾を省いて
  表示される（テストのフォントで測った。2026-10-03）。読み上げは名前を全文で読む
